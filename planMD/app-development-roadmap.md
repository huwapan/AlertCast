## この計画書について
- アプリ全体を **どの順番で作るか** と、**その理由** をまとめた計画書。ロードマップは、目的地までの道のりと順番を書いた予定表のこと。
- 同じことを2か所に詳しく書くと食い違いやすいので、文書ごとに書くことを分ける。

| 文書 | 書くこと |
|---|---|
| [docs/storymap.md](../docs/storymap.md) | 何を作るか、それができたか |
| この計画書 | どの順番で作るか、その理由、作る前に決めること |
| 機能ごとの計画書（`planMD/NNN_名前.md`） | どう作るか、作業中に何があったか（失敗と修正も） |

### 更新のルール
- 機能の PR がマージされたら、次の作業のブランチの最初のコミットで、この計画書のチェックを付けて「今いるところ」を直す。
- 機能を作り始めたら、その機能の計画書へのリンクを足す。
- 順番を変えたら、下の「変更履歴」に日付と理由を書く。
- まだ決まっていないことは「作る前に決めること」に書き、決まったことのように書かない。

## ストーリーマップの段の読み方
- タスク（例：「予定を入力する」）の下の **入れ子の深さが、そのまま段** になる。深さ1が1段目、深さ2が2段目。
- `^` が付いた項目は1段上へ、`v` が付いた項目は1段下へずれる。
- 例：「入力 > 予定を入力する」の下にある3つの項目
  - 「文字で入力」：深さ1なので **1段目**
  - 「^ 期限を入力」：深さ2で `^` が付いているので **1段目**
  - 「優先度を入力」：深さ3なので **3段目**
- 1段目が **ウォーキングスケルトン**（各機能の最小限を、画面から DB まで端から端までつないだもの）。

### [ ] 1. 想起：^ 長く放置されている予定を教える

- 作る前に決めること：（決まった。くわしくは計画書）

## 全体の見直し（2段目のあと）

### 見直しの候補
- [ ] 期限で終わらせる予定（`deadline`）と、一日単位の予定（`all_day`）の登録画面がない
- [ ] 編集ページの「予定の復元フォーム」が仮の文字のまま

- [ ] CSS がほぼ空で、画面の見た目が整っていない
- [ ] `schedule-edit.html` だけ `<!DOCTYPE html>` と `lang="ja"` がなく、ホームへのリンクが「home」になっている
- [ ] 登録・変更で入力エラーになると、入力した内容が消える
- [ ] 完了にした予定を未完了に戻せない
- [ ] テストのスクリプトが一時フォルダーにあり、リポジトリに残っていない（README では `tests/` に置く予定）
