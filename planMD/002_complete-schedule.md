# 002 予定完了を通知を出してボタン操作で確認する

- ストーリー：[docs/storymap.md](../docs/storymap.md) の「確認 > 予定完了を確認する > 予定完了を通知を出してボタン操作で確認する」
- ブランチ：`feature/complete-schedule`
- 状態：完了（ブラウザでの確認済み、PR でレビュー待ち）

## 背景
- ウォーキングスケルトンの残りは、**確認（完了）**、想起（今日の予定と期限超過）、変更。
- 完了から作る理由：想起の「期限を超過している予定を教える」は、予定が完了したかどうかが分からないと判定できないため。

## 決めたこと
- 完了の操作は **ホーム画面に通知を出して、その場のボタンで行う**（storymap の「通知を出してボタン操作で確認する」に合わせる）。
- 通知に出す予定：終了日時を過ぎていて、まだ完了も削除もしていない時間指定予定。
- ホームは DB を読む必要があるので、`index.html` を `index.php` に名前を変える（`git mv` で履歴を残す）。
- 完了日時は `completed_at` 列（001 で作成済み）に `Asia/Tokyo` の `Y-m-d H:i:s` で記録する。マイグレーションは不要。
- `show-table.php`（予定一覧）は見るためのページのまま。完了したかどうかが分かるように「状態」列だけ足す（ボタンは付けない）。

## 失敗したことと修正したこと

### 1. テストで、DB にあるのはテスト予定だけだと思い込んでいた
- 起きたこと：予定一覧の「状態」を確かめるテストで、「未完了が2件、完了が0件」のように表全体の数を数えたら NG になった。
- 原因：DB には、ブラウザで登録された本物の予定（買い出し・犬の散歩など）も入っていた。それらも「未完了」と表示されるので、数が合わなかった。アプリの表示は正しかった。
- 修正：表全体の数ではなく、テスト予定のタイトルの行だけを取り出して「状態」を確かめるようにした。通知の件数も、決め打ちの「1件」ではなく、DB から「終わっていて未完了・未削除の予定」の数を数えて比べるようにした。
- 教訓：本物のデータが入っている DB でテストするときは、テストで作ったデータだけを対象に確かめる。テスト後も、DB をまるごとバックアップに戻すとその間に登録された本物の予定まで消えてしまうので、テストで作った行だけを消す。

### 2. テスト用スクリプトで PHP 8.5 の非推奨の警告が出た
- 起きたこと：テストに使った PHP スクリプトで「`$http_response_header` は非推奨（今後なくなる予定）」という警告が出た。
- 修正：代わりの `http_get_last_response_headers()` を使うように直した。アプリのコードではなく、テスト用スクリプトだけの問題だった。
- 教訓：PHP のバージョンが上がると、昔からある書き方が非推奨になることがある。警告が出たら、メッセージに書かれている代わりの方法を使う。

### 3. 前回までのテスト方法（curl）をやめて、PHP のスクリプトでテストした
- 001 で、Windows の curl は日本語を Shift_JIS で送って文字化けすることが分かっていた（001 の「失敗したことと修正したこと」の3）。
- 今回は最初から PHP のスクリプトで HTTP リクエストを送ってテストした。PHP なら日本語をそのまま UTF-8 で送れるので、文字化けは起きなかった。
